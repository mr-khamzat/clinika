# Резервное копирование и восстановление

## Зачем

Данные пациентов и клиники — основной актив платформы. Потеря части базы из-за сбоя диска, человеческой ошибки или вредоносной активности недопустима. Система резервного копирования платформы спроектирована так, чтобы любую запись за последние 30 дней можно было восстановить с точностью до 6 часов.

## Архитектура бэкапов

```
PostgreSQL → pg_dump (каждые 6 часов)
            → GPG (асимметричное шифрование)
            → rclone → удалённое S3-совместимое хранилище
              (отдельный физический сервер, другой регион)
```

Дополнительно:

- Файлы пользователей (PDF документов, аватары) — синхронизация ежедневно.
- Wiki контент и регламенты — git-репозиторий с push в защищённый remote.
- Конфигурация nginx, docker-compose — git.

## Расписание

| Объект | Частота | Хранение |
|---|---|---|
| PostgreSQL full | 6 часов | 30 дней rolling |
| PostgreSQL WAL | потоково | 7 дней |
| Файлы пользователей | 24 часа | 30 дней rolling |
| Wiki / конфиги (git) | при изменении | бессрочно |
| Логи nginx | 24 часа | 7 дней |

## Шифрование

GPG ключ платформы — асимметричный (RSA 4096):

- Публичный ключ хранится на сервере, используется для шифрования бэкапов.
- Приватный ключ — **не на сервере**. Хранится у владельца платформы offline (USB в сейфе) и в зашифрованном хранилище менеджера паролей.

Без приватного ключа расшифровать бэкап невозможно даже при доступе к удалённому хранилищу.

## Удалённое хранилище

S3-совместимое хранилище от провайдера, отличного от провайдера хостинга. Доступ — IAM ключ с правом только PUT/GET в одно конкретное «ведро». DELETE отключён (защита от ransomware).

## Восстановление

### Полный откат

```bash
# 1. Скачать нужный снимок
rclone copy remote:clinika-backups/2026-05-09T18.dump.gpg /tmp/

# 2. Расшифровать
gpg --decrypt /tmp/2026-05-09T18.dump.gpg > /tmp/dump.sql

# 3. Остановить приложение
docker compose stop clinika-backend

# 4. Восстановить
psql clinika < /tmp/dump.sql

# 5. Поднять
docker compose up -d clinika-backend
```

Время восстановления (RTO) на боевом сервере — около 20-40 минут для базы до 50 GB.

### Восстановление конкретной таблицы

Когда нужно восстановить только одну таблицу (например, случайно удалили пациентов одной клиники):

```bash
# 1. Восстановить дамп в отдельную БД
createdb clinika_restore
gpg --decrypt /tmp/dump.gpg | psql clinika_restore

# 2. Извлечь нужные данные
pg_dump -t patients clinika_restore | psql clinika

# 3. Выровнять id, если нужно (ручной SQL)
```

### Point-in-time recovery

WAL архивируются непрерывно, что позволяет восстановиться на любой момент в пределах 7 дней. Используется при ошибочной транзакции, замеченной не сразу.

```bash
# 1. Восстановить последний полный дамп до точки X
# 2. Применить WAL до timestamp Y
psql -c "SELECT pg_xlog_replay_resume();"
```

## Тестирование

Каждые 7 дней автоматически:

1. Берётся последний снимок.
2. Восстанавливается в изолированную тестовую БД.
3. Запускается набор санитарных тестов (counts, схема, индексы).
4. Результат пишется в audit log.

Если тест не прошёл — алерт в Telegram super_admin.

## Disaster recovery

Если основной сервер полностью недоступен:

1. Поднять новый сервер по той же спецификации.
2. Развернуть docker-compose из git-репозитория.
3. Расшифровать последний бэкап (GPG ключ из сейфа).
4. Восстановить БД.
5. Сменить DNS на новый IP.
6. Прогнать smoke-тесты.

RTO для disaster recovery — 4-8 часов в зависимости от размера БД и доступности владельца GPG-ключа.

## Что НЕ восстанавливается

- Истёкшие токены сессий (пользователи перелогинятся).
- Кеш Redis (наполнится снова).
- Realtime WebSocket-сессии (клиенты переподключатся).
- Логи приложения старше 7 дней.
- Аудио-файлы записанных звонков старше 30 дней (отдельная политика хранения).

## Безопасность процесса

- Резервные копии не должны содержать дешифрованный GPG ключ.
- Логи rclone маскируют пути и не светят учётки.
- Доступ к удалённому S3 — только sa с IAM политикой, отдельный для backup-pipeline.
- Чтение/восстановление вручную записывается в audit_log как высокоприоритетное событие.

## Метрики

В Grafana отображаются:

- Время последнего успешного бэкапа.
- Размер дампа (тренд для wraparound).
- Длительность тестового восстановления.
- Количество объектов в удалённом S3.

При отсутствии нового бэкапа более 12 часов — критический алерт.

## FAQ

**Что если потеряли GPG ключ?** Бэкапы становятся бесполезны. Поэтому ключ ОБЯЗАТЕЛЬНО храним в нескольких местах: USB в сейфе + менеджер паролей + у второго доверенного лица.

**Можно ли восстановить данные одного тенанта без затрагивания других?** Да, через метод «восстановление таблицы» с фильтром по `tenant_id`.

**Когда последний раз был тест восстановления?** Метрика `last_backup_test_at` в `/admin/system/status`.

**Кто может инициировать restore?** Только super_admin, и только через консольный скрипт на сервере (не через UI). Это намеренное ограничение.
