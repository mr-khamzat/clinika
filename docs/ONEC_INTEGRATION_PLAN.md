# План: Интеграция с 1С (двухсторонняя синхронизация)

**Версия:** 0.1 (draft) · **Дата:** 2026-05-15
**Связан с:** [INVENTORY_COST_PLAN.md](INVENTORY_COST_PLAN.md), [DIRECTOR_CABINET_PLAN.md](DIRECTOR_CABINET_PLAN.md)

## 1. Цель

Двухсторонняя синхронизация Клиники с 1С:Бухгалтерия / 1С:Управление торговлей
для:
- импорта номенклатуры (товаров) и **первичной заливки склада** из Excel/CSV
  выгрузки (одной кнопкой, без ручного ввода)
- последующего регулярного обмена документами (приходы, списания, продажи)
- движения по бухгалтерским счетам в реальном времени

> **Принцип:** в Клинике источник правды для медицинских данных (приёмы,
> услуги, пациенты). В 1С — источник правды для бухгалтерии (баланс, налоги).
> Складские остатки **синхронизируются** в обе стороны.

## 2. Этап 0: Импорт из 1С Excel (ПЕРВЫЙ КРИТИЧНЫЙ СЦЕНАРИЙ)

Раньше всех бухгалтерских танцев — нужна простая кнопка **«Импортировать
номенклатуру и остатки из 1С»**. Это покрывает 90% реальной потребности:
бухгалтерия даёт выгрузку → руководитель льёт её в Клинику → склад заполнен.

### 2.1. Типовые форматы 1С-выгрузки

1С умеет экспортировать в:
- **`xlsx`** (Excel) — самый частый вариант, отчёт «Остатки на складе»
- **`csv`** (с разделителем `;`, кодировка `Windows-1251`)
- **`xml`** в формате `КоммерческаяИнформация` (CommerceML 2)
- **`xml`** в формате `EnterpriseData` (новый стандарт 1С 8.3+)

**Для Этапа 0 поддерживаем только xlsx и csv.** XML — на следующем этапе.

### 2.2. Колонки типовой выгрузки

Стандартная выгрузка «Остатки по номенклатуре» из 1С имеет колонки:

| 1С-название | Наш атрибут | Обяз. |
|---|---|---|
| Артикул / Код | `inventory_items.sku` | ✅ |
| Наименование | `inventory_items.name` | ✅ |
| Единица измерения | `inventory_items.unit` | ✅ |
| Цена закупки | `inventory_batches.unit_cost` | ⚠️ (без неё себестоимость = 0) |
| Количество / Остаток | `inventory_batches.qty_received` | ✅ |
| Группа / Категория | `inventory_items.category` (mapping) | ⏤ |
| Серия / Партия | `inventory_batches.batch_number` | ⏤ |
| Срок годности | `inventory_batches.expires_at` | ⏤ |
| Поставщик | `suppliers.name` (поиск/создание) | ⏤ |
| Штрихкод | `inventory_items.barcode` | ⏤ |
| НДС | (опускаем) | ⏤ |
| Склад | `clinic_id` (mapping на клинику) | ⏤ |
| ID в 1С | `inventory_items.external_id` | ⏤ |

### 2.3. UI флоу «Импорт из 1С» (Manager-кабинет)

1. **Шаг 1: Загрузка файла**
   - Кнопка «📂 Импорт из 1С» → выбор `.xlsx` / `.csv` файла
   - Превью первых 10 строк
   - Выбор листа Excel (если несколько)

2. **Шаг 2: Маппинг колонок**
   - Система предлагает автомаппинг по заголовкам (например, «Артикул» →
     `sku`, «Остаток» → `quantity`)
   - Пользователь подтверждает / правит
   - Сохранение пресета маппинга для следующих импортов

3. **Шаг 3: Параметры импорта**
   - Куда зачисляем остатки: какая клиника / какой склад
   - Что делать с существующими SKU:
     - `skip` — пропустить (только новые)
     - `update` — обновить имя/цену, остатки прибавить
     - `replace` — заменить (с реверсом старых партий)
   - Дата прихода: текущая / из колонки / выбрать руками
   - Поставщик по умолчанию (если в файле нет)
   - Категория по умолчанию (если в файле нет)

4. **Шаг 4: Preview & валидация**
   - Таблица: «Будет создано N новых, обновлено M, пропущено K»
   - Список ошибок: «Строка 17: пустой артикул», «Строка 42: дубликат SKU»
   - Кнопки: «Отменить» / «Импортировать»

5. **Шаг 5: Импорт**
   - Прогресс-бар (если > 100 строк)
   - Результат: «✅ Импортировано 543 позиции, создано 543 партий»
   - Лог сохраняется в `inventory_import_logs` (для отката одной кнопкой)

### 2.4. Бэкенд

```python
# REST endpoints
POST   /inventory/import/preview      # парсит файл, возвращает превью + маппинг
POST   /inventory/import/execute      # выполняет импорт по подтверждённому маппингу
GET    /inventory/import/history      # лог импортов
POST   /inventory/import/{id}/rollback  # откатить импорт (если ничего не списано после)
```

```sql
CREATE TABLE inventory_import_logs (
  id UUID PRIMARY KEY, tenant_id UUID, clinic_id UUID,
  source VARCHAR(50),    -- '1c_xlsx' / '1c_csv' / '1c_xml'
  file_name VARCHAR(255), file_hash VARCHAR(64),
  rows_total INT, rows_created INT, rows_updated INT, rows_skipped INT, rows_failed INT,
  mapping_used JSONB,
  status VARCHAR(20),    -- pending / completed / failed / rolled_back
  created_by_id UUID, created_at TIMESTAMPTZ,
  result_summary JSONB,
  errors JSONB
);
```

**Алгоритм:**
- Парсим файл с помощью `openpyxl` (xlsx) или `pandas` (csv с автоопределением кодировки)
- По `mapping_used` строим список `RowDTO`
- Транзакция: создаём `inventory_items` (или обновляем), создаём `inventory_batches`
  для остатков, создаём `inventory_movements (income)` с пометкой `source='1c_import'`
- Поставщиков ищем по имени, создаём если нет
- В случае ошибки на строке — записываем в `errors[]`, продолжаем импорт остальных

### 2.5. Идемпотентность

- Хеш файла (SHA-256) пишется в `file_hash`. Повторная загрузка того же
  файла — предупреждение «Этот файл уже импортировался N дней назад».
- Можно прокинуть `external_id` (ID товара в 1С) — тогда повторный импорт
  той же выгрузки за тот же период обновит, а не задвоит.

## 3. Этап 1: Регулярный экспорт в 1С (одностороннее)

После Этапа 0 — обратное направление: данные из Клиники → 1С.

### 3.1. Что выгружаем
- Реализация услуг (выручка) → акт оказания услуг в 1С
- Поступление товара (приходы на склад) → накладные
- Списание материалов → акты списания
- Платежи (нал/безнал) → банковская выписка / приходный кассовый ордер
- Зарплатные начисления → ведомость

### 3.2. Формат выгрузки
- **EnterpriseData XML** (стандарт 1С 8.3, поддерживается всеми типовыми
  конфигурациями) — рекомендуется для долгой жизни
- **CSV / Excel** простыми отчётами — на случай если в 1С старая версия

### 3.3. Регламент
- По запросу: кнопка «Выгрузить за период» в Manager-кабинете
- По расписанию (cron): ежедневная выгрузка в `/var/exchange/1c/outbox/`
- Через webhook: при `accounting_period.closed` сразу формируем пакет

## 4. Этап 2: Полная двухсторонняя синхронизация

### 4.1. Архитектура

```
┌─────────────┐         ┌──────────────────┐         ┌─────────┐
│   Клиника   │ ───→    │  Adapter Layer   │  ──→    │  1С     │
│  (FastAPI)  │ ←───    │  (sync_queue +   │  ←──    │ (HTTP-  │
│             │         │   mappings)      │         │  сервис)│
└─────────────┘         └──────────────────┘         └─────────┘
```

### 4.2. Технические варианты обмена

| Вариант | Плюсы | Минусы |
|---|---|---|
| **HTTP-сервис в 1С** | Реалтайм, стандарт для 8.3 | Нужна доработка 1С, не у всех бухгалтерий |
| **EnterpriseData XML через папку** | Без доработок 1С | Только пакетный обмен, лаг 5-60 мин |
| **Шина данных** (RabbitMQ / Kafka) | Высокая надёжность | Дорого разворачивать |
| **Сторонний коннектор** (1С:Шина, МойСклад API) | Out-of-the-box | Зависимость от вендора, оплата |

**Рекомендация для нашего масштаба:**
- **Default**: EnterpriseData XML через файловый обмен (универсально, простой)
- **Premium**: HTTP-сервис для клиник с современной 1С 8.3 (на платных тарифах)

### 4.3. Очередь синхронизации

```sql
CREATE TABLE onec_sync_queue (
  id UUID PRIMARY KEY, tenant_id UUID,
  direction VARCHAR(10),    -- 'out' (в 1С) / 'in' (из 1С)
  entity_type VARCHAR(50),  -- 'item' / 'batch' / 'movement' / 'receipt' / 'payment'
  entity_id UUID,
  payload JSONB,
  status VARCHAR(20),       -- pending / processing / done / error / dead
  attempts INT DEFAULT 0,
  last_error TEXT,
  external_id VARCHAR(100), -- ID в 1С после успеха
  enqueued_at TIMESTAMPTZ, processed_at TIMESTAMPTZ,
  next_retry_at TIMESTAMPTZ
);
```

Worker (asyncio task / celery beat) — берёт batch из очереди, формирует
XML/JSON, отправляет, обновляет статус.

### 4.4. Маппинг сущностей

```sql
CREATE TABLE onec_mappings (
  id UUID PRIMARY KEY, tenant_id UUID,
  entity_type VARCHAR(50),    -- 'item' / 'supplier' / 'user' / ...
  local_id UUID,              -- наш UUID
  onec_id VARCHAR(100),       -- GUID в 1С
  onec_code VARCHAR(50),      -- код/артикул в 1С
  last_sync_at TIMESTAMPTZ,
  conflict_marker VARCHAR(20) -- если есть конфликт: 'local' / 'onec' / 'manual'
);
```

### 4.5. Разрешение конфликтов

При двухстороннем обмене возможен сценарий: пока мы передаём данные в 1С,
там кто-то поменял те же поля.

**Стратегии:**
- `last-write-wins` (по timestamp) — простой, но рискованный
- `clinika-wins` для медицинских данных, `onec-wins` для бухгалтерских
- **Ручное разрешение** через UI — для редких конфликтов выводим
  «требует решения», бухгалтер выбирает

Рекомендация: hybrid (по типу сущности — разные правила) + UI для ручного разруливания.

## 6. Открытые вопросы для клиента (бухгалтера)

Перед началом Этапа 1+ нужно узнать у бухгалтерии каждой клиники:
1. Какая версия 1С (Бухгалтерия 3.0 / УТ / другая)?
2. Какая редакция (БазовАЯ / ПРОФ / КОРП)? Базовая не поддерживает HTTP-сервисы.
3. Есть ли уже автоматический обмен с чем-то (мой склад, Битрикс)?
4. Какие конкретные документы хочет видеть бухгалтер?
5. Кто контактное лицо на стороне 1С (программист 1С или франчайзи)?

## 7. Что НЕ делаем

- ❌ Реализация полноценной кассы 1С — пока только склад и движение товаров
- ❌ Зарплатный модуль 1С:ЗУП — отдельная задача, после стабилизации основ
- ❌ ЕГАИС/Маркировка — медицина без алкоголя, для расходников не обязательно
- ❌ Обмен с банк-клиентом 1С — пока не наша зона
