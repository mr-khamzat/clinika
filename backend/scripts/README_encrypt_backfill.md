# Backfill шифрования историчных ПДн — `encrypt_pii_backfill`

Разовый (идемпотентный) скрипт, который шифрует **существующие** строки ПДн,
созданные ДО деплоя шифрования. Закрывает находки **#2 / #17 / #18** (152-ФЗ).

Файл: `backend/scripts/encrypt_pii_backfill.py`

## Зачем он нужен

Миграции уже добавили shadow-колонки `*_encrypted` / `*_hash`, а listener
`app/services/pii_sync.py` шифрует **новые и изменяемые** записи прозрачно.
Но **старые** строки остаются с пустыми shadow-колонками. Шифровать их прямо в
DDL-миграции нельзя (нужен стабильный `SECRET_KEY` и контролируемое окно), поэтому
backfill вынесен в отдельный data-скрипт.

## Что шифруется

Карта полей берётся 1:1 из `pii_sync._MAP` (единый источник истины — backfill и
listener не могут разойтись):

| Таблица                 | Шифруемые поля                                  | Blind-index `*_hash` |
|-------------------------|-------------------------------------------------|----------------------|
| `appointments`          | `patient_phone`, `patient_name`, `notes`        | phone, name          |
| `patient_diagnoses`     | `name`, `notes`                                 | —                    |
| `patient_allergies`     | `allergen`, `reaction`                          | —                    |
| `patient_vaccinations`  | `vaccine_name`                                  | —                    |
| `lab_results`           | `value`, `reference_range`, `raw_json` (JSONB)  | —                    |
| `patient_vitals`        | `value_extra` (JSONB), `note`                   | —                    |
| `patient_accounts`      | `name`                                          | name                 |

- JSONB-поля (`raw_json`, `value_extra`) сериализуются в JSON-строку и шифруются —
  как это делает listener (getter обратно `json.loads(decrypt(...))`).
- Plaintext-колонки **НЕ переименовываются и НЕ удаляются** — это сделает поздняя
  миграция уже после успешного backfill.
- Структурированные/служебные поля (`icd10_code`, `test_code`, `unit`,
  `value_num`, `flagged`, `metric`, …) НЕ шифруются — так и задумано.

## Требования (обязательно перед запуском)

1. **Бэкап БД.** Сделайте дамп Postgres до запуска (`pg_dump`). Скрипт идемпотентен,
   но это необратимое изменение данных.
2. **Стабильный `SECRET_KEY`.** Ключ Fernet и blind-index `*_hash` деривируются из
   `settings.secret_key`. После backfill его **нельзя менять** — иначе шифртекст
   не расшифруется, а хэши перестанут совпадать. Используйте тот же ключ, что и
   на проде.
   - Если `SECRET_KEY` пуст/недоступен, `encryption_service` отдаёт `plain:<value>`.
     Такие поля скрипт **не считает зашифрованными** и при следующем (уже
     корректно настроенном) прогоне перешифрует. Поэтому **не запускайте на
     запись без рабочего ключа.** Сначала `--dry-run`.
3. **Миграции применены.** Shadow-колонки `*_encrypted`/`*_hash` уже должны
   существовать (миграции #2/#17/#18). Иначе скрипт упадёт на отсутствующей колонке.
4. **Maintenance-окно.** Запускать при низкой нагрузке. Скрипт берёт строки
   батчами и коммитит по батчу; конкуренция с пишущим трафиком возможна, но
   повторный прогон безопасно доберёт остаток.

## Порядок деплоя (рекомендуемый)

1. Применить миграции shadow-колонок (#2/#17/#18). **alembic не трогаем — уже сделано.**
2. Включить listener `install_pii_sync()` (новые записи шифруются с этого момента).
3. Сделать бэкап БД.
4. **Dry-run** backfill — оценить объём:
   ```
   docker compose exec clinika-backend python -m scripts.encrypt_pii_backfill --dry-run
   ```
5. **Боевой прогон** backfill в maintenance-окне:
   ```
   docker compose exec clinika-backend python -m scripts.encrypt_pii_backfill
   ```
6. (Опционально) повторить прогон для контроля — должен показать 0 затронутых строк.
7. Только ПОСЛЕ этого переключать чтение исключительно через `*_plain`-property и
   планировать позднюю миграцию drop plaintext-колонок.

## Запуск

```bash
# Сухой прогон — только счёт, НИЧЕГО не пишет:
python -m scripts.encrypt_pii_backfill --dry-run

# Боевой backfill всех таблиц:
python -m scripts.encrypt_pii_backfill

# Только одна таблица:
python -m scripts.encrypt_pii_backfill --only appointments

# Свой размер батча (по умолчанию 500):
python -m scripts.encrypt_pii_backfill --batch-size 1000
```

В контейнере при необходимости: `cd /app && python -m scripts.encrypt_pii_backfill`.

Доступные значения `--only`: `appointments`, `patient_diagnoses`,
`patient_allergies`, `patient_vaccinations`, `lab_results`, `patient_vitals`,
`patient_accounts`.

## Идемпотентность

Скрипт безопасно перезапускать сколько угодно раз. Решение принимается **по полю**,
а не по строке:

- Поле берётся в работу, только если его `*_encrypted` **ещё не** начинается с
  `enc:` (т.е. `NULL`, legacy без префикса или `plain:`) **И** есть непустой
  plaintext-источник.
- Уже зашифрованные (`enc:...`) поля **пропускаются** — повторный прогон их не трогает.
- Пустые/`NULL` plaintext не трогаются (shadow остаётся `NULL`).
- Частично зашифрованные строки (одно поле `enc:`, другое ещё нет) корректно
  доводятся до конца.

Поэтому прогон после сбоя/аварии просто доберёт незавершённые строки.

## Поведение и заметки

- **Прогресс** логируется по каждому батчу и итогом по таблице/всем таблицам.
- **`--dry-run`** делает `rollback()` после каждого батча — гарантированно ничего
  не пишет, только считает строки/поля к шифрованию.
- **RLS / тенанты.** Скрипт использует `AsyncSessionLocal` без HTTP-контекста →
  `app.tenant_id=''` → RLS permissive, видны строки **всех тенантов**. Для
  системного backfill это корректно (см. `app/database.py`, раздел про фоновые
  джобы). Запускать только как доверенную обслуживающую задачу.
- **Шифрование идентично listener'у** (`pii_sync._enc` + те же `hash_*`), поэтому
  значения совместимы; `before_update`-listener при коммите перепишет те же
  shadow-колонки тем же результатом — конфликта нет.
- Скрипт **не падает** на `NULL`/пустых значениях и не пишет `plain:` поверх
  существующего `enc:`.
