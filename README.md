## Роли и кабинеты

| Роль | Кабинет | Описание |
|------|---------|----------|
| `super_admin` | Платформа (AdminLayout) | Управление тенантами, биллинг платформы, метрики |
| `manager` | Панель руководителя (AdminLayout) | Полное управление тенантом |
| `admin` | Панель администратора (AdminLayout) | Работа с направлениями и пациентами |
| `partner` | Партнёрский портал | Создание направлений, просмотр статистики |
| `patient` | Личный кабинет пациента | Просмотр своих направлений и данных из МИС |

### Разграничение доступа к разделам

**Super Admin** видит: всё + раздел "Платформа" с управлением тенантами, активацией подписок, метриками платформы.

**Manager** видит: главная, сотрудники, клиники, направления, отчёты, аналитика, бонусы, партнёры, услуги, скидки, реестр, расписание, МИС Sync, Звонки/SMS, Плагины, Аудит, Биллинг.

**Admin** видит: направления, бонусы, QR-сканирование, клиники (только для выбора), расписание (только просмотр).

## Направления пациентов

Центральный модуль платформы — направления пациентов между клиниками.

### Жизненный цикл

```
created → confirmed → expired (7 дней без подтверждения)
       ↘ cancel_requested → cancelled (одобрено руководителем)
                          → confirmed (отклонено руководителем)
```

### Функции

- **Создание направления**: выбор клиники-получателя, услуги, телефон пациента, дата приёма
- **Поиск пациента в МИС**: при вводе телефона автоматически подгружаются данные из МИС Renovatio
- **QR-код**: генерация QR с HMAC-подписью (`REF:<uuid>:<hmac_16>`), защита от подделки
- **Подтверждение**: по QR-скану или 5-значному короткому коду
- **Статус "принят врачом"**: расширенный статус при наличии расписания
- **Комментарии**: к направлению (admin/manager)
- **Отмена**: запрос от admin → одобрение/отклонение от manager
- **История пациента**: направления с фильтром по статусу, дате, клинике
- **Автоподтверждение из МИС**: polling МИС каждые N минут, автоматическое подтверждение при нахождении визита
- **Направления к себе**: клиника может направлять к себе (опционально)

### API

```
POST /referrals/                     — создать направление
GET  /referrals/                     — мои направления (по admin)
POST /referrals/scan                 — подтвердить по QR
POST /referrals/confirm-by-code      — подтвердить по коду
GET  /referrals/{id}                 — детали
POST /referrals/{id}/cancel-request  — запросить отмену
GET  /referrals/verify-patient       — найти пациента в МИС по телефону
```

## Бонусная система

- **Начисление**: при каждом подтверждении направления, по правилу категории услуги
- **Типы бонуса**: `regular` (фиксированный в рублях), `commission` (% от стоимости услуги)
- **Категории**: разные ставки для разных категорий услуг
- **Статусы**: `pending` (ожидает выплаты) → `paid` (выплачен) / `cancelled`
- **Выплаты**: массовая выплата всем pending-бонусам сотрудника или выборочная
- **Запрос отмены**: admin запрашивает отмену бонуса → manager одобряет/отклоняет
- **Баланс**: сводка по каждому сотруднику (начислено / выплачено / pending)
- **Разрез по клиникам**: фильтрация по клинике-источнику и клинике-получателю

### API

```
GET  /manager/bonuses/              — список бонусов с фильтром
POST /manager/bonuses/pay           — выплатить бонус(ы)
GET  /manager/bonuses/summary       — сводка по сотруднику
POST /manager/cancel-requests/{id}/approve — одобрить отмену
POST /manager/cancel-requests/{id}/reject  — отклонить отмену
```

## Персонал и клиники

### Сотрудники

- **Роли**: `admin` (сотрудник), `manager` (руководитель)
- **Создание**: вручную (username+password, Telegram ID, или оба)
- **Привязка к клинике**: каждый admin привязан к своей клинике
- **Деактивация**: мягкое (`is_active=False`) или жёсткое (удаление данных, `[Удалён]`)
- **Видимость деактивированных**: только super_admin в разделе "Платформа"
- **Аудит**: все создания/изменения/деактивации пишутся в audit_log
- **Категория**: `doctor` / `nurse` — для внутренней классификации

### Клиники

- **CRUD**: создание, редактирование, деактивация
- **Деактивация**: `is_active=False` — клиника скрывается во всех кабинетах
- **МИС-привязка**: поле `mis_id` для связи с клиникой в МИС
- **Видимость**: настройка (`clinic_visibility`) — какие клиники видит каждая другая клиника
- **Расписание работы**: часы работы по дням недели

### API

```
GET    /admins/              — список активных сотрудников
POST   /manager/admins/      — создать сотрудника
PATCH  /manager/admins/{id}  — обновить сотрудника
DELETE /manager/admins/{id}  — деактивировать/удалить
GET    /manager/clinics/     — список клиник
POST   /manager/clinics/     — создать клинику
PATCH  /manager/clinics/{id} — обновить/деактивировать клинику
```

## МИС-интеграция (Renovatio)

Интеграция с МИС Renovatio через REST API (`/api/public/METHOD`, POST form-data с `api_key`).

### Доступные методы МИС

| Метод МИС | Что делает | Используется |
|-----------|-----------|--------------|
| `getClinics` | Список клиник с адресами | Импорт клиник |
| `getUsers` | Список пользователей (врачи) | Импорт врачей |
| `getServices` | Услуги клиники с категориями и ценами | Импорт услуг |
| `getPatient` | Данные пациента по телефону | Личный кабинет, поиск |
| `getAppointments` | Записи пациента | Автоподтверждение, история |
| `createAppointment` | Создать запись | (будущее) |
| `cancelAppointment` | Отменить запись | (будущее) |

### Синхронизация клиник

1. Раздел **МИС Sync → Клиники** — список всех клиник из МИС
2. Выбор нужных чекбоксами → "Импортировать"
3. Клиники создаются/обновляются в нашей БД с `mis_id`
4. Деактивация — через раздел Клиники → "Изменить" → toggle "Статус"

### Синхронизация врачей

1. Раздел **МИС Sync → Врачи** — список врачей из МИС
2. Синхронизация создаёт записи в таблице `doctors`
3. Поле `mis_id` связывает врача с МИС
4. Для создания личного кабинета врача — создать User через раздел Сотрудники
5. В будущем: автоматическое создание User при импорте врача

### Синхронизация услуг

1. Раздел **МИС Sync → Услуги** — список услуг конкретной клиники МИС
2. Фильтр по категориям + конкретным услугам
3. Выбор целевых клиник нашей сети
4. Услуги синхронизируются с полями: название, категория, цена, описание, лаборатория, длительность

### Автоподтверждение направлений

- Фоновый polling МИС каждые **N минут**
- Проверяет завершённые визиты в МИС
- Если находит совпадение с нашим направлением — автоматически подтверждает
- Ручной запуск: **МИС Sync → Инструменты → Запустить поллинг**

### API

```
GET  /mis/clinics              — список клиник МИС
POST /mis/clinics/sync         — импортировать выбранные клиники
GET  /mis/doctors              — список врачей МИС
POST /mis/doctors/sync         — импортировать врачей
GET  /mis/services             — услуги МИС (параметр: clinic_mis_id)
POST /mis/services/sync        — импортировать услуги
GET  /mis/patient/profile      — данные пациента по телефону
GET  /mis/patient/appointments — история визитов пациента
POST /mis/poll-referrals       — запустить поллинг МИС
```

### Расширяемость (новые МИС)

Для добавления новой МИС:
1. Создать `app/services/mis_client_NEW.py` с функциями `get_clinics()`, `get_users()`, `get_services()`, `get_patient()`, `get_appointments()`
2. Создать `app/services/mis_sync_service_NEW.py` аналогично существующему
3. Добавить новый роутер `/mis-new/` с теми же endpoint-ами
4. Добавить конфигурацию МИС в settings (базовый URL, api_key, тип аутентификации)

## Расписание врачей

Модуль управления временными слотами врачей и записями пациентов.

### Структура данных

- **Doctor** — врач (clinic_id, specialty, slot_duration, mis_id)
- **DoctorSchedule** — расписание на дату (doctor_id, date, start_time, end_time, break_start/end)
- **Appointment** — запись пациента (doctor_id, patient_phone, datetime, status, source: online/admin/mis)

### Функции

- **Управление расписанием** (manager): создание/редактирование расписания врача по дням
- **Просмотр слотов** (admin, при создании направления): видит доступные слоты выбранного врача
- **Личный кабинет врача**: врач видит только своё расписание на неделю/месяц
- **Запись пациентов**: admin записывает пациента на слот в момент создания направления
- **Самозапись пациента**: через личный кабинет (mini-app)

### Видимость по ролям

| Роль | Что видит |
|------|-----------|
| Manager | Расписание всех врачей, создание/редактирование |
| Admin | Только слоты выбранного врача (при создании направления) |
| Doctor (User с ролью admin + категория doctor) | Только своё расписание |
| Patient | Свободные слоты для записи |

### API

```
GET  /scheduling/doctors          — список врачей (с фильтром по клинике)
POST /scheduling/doctors          — создать врача
PUT  /scheduling/doctors/{id}     — обновить врача
GET  /scheduling/slots            — доступные слоты (doctor_id, date)
POST /scheduling/schedules        — создать расписание врача
GET  /scheduling/appointments     — список записей
POST /scheduling/appointments     — создать запись
PATCH /scheduling/appointments/{id} — обновить статус записи
```

## P2P Звонки и статусы присутствия

Система WebSocket-based сигналинга для P2P аудио/видео звонков между сотрудниками.

### Статусы присутствия

| Статус | Описание | Влияние на звонки |
|--------|----------|-------------------|
| `online` | На месте, доступен | Принимает входящие |
| `away` | Не на месте | Входящие отклоняются (сигнал "не на месте") |
| `busy` | Занят (в звонке, на приёме) | Входящие отклоняются (сигнал "занят") |
| `offline` | Не в системе | Входящие не доставляются |

**Автоматические переходы:**
- Принял звонок → `busy` (на время разговора)
- Завершил звонок → возврат к `online`
- Нет активности 30 мин → `offline`

### Матрица разрешений звонков

Настраивается в разделе **Звонки/SMS → Разрешения звонков**:
- Строки: кто звонит
- Столбцы: кому можно позвонить
- Параметры: аудио, видео, только своя клиника

Роли в матрице: `admin`, `manager`, `partner`, `doctor`

### Протокол сигналинга (WebSocket)

```
ws://.../presence/ws/{user_id}

Клиент → Сервер:
  heartbeat           — keep-alive каждые 30 сек
  call_invite         — инициировать звонок (to_user_id, call_type: audio/video)
  call_accept         — принять входящий звонок
  call_reject         — отклонить звонок
  call_end            — завершить звонок
  call_busy           — сигнал "занят"

Сервер → Клиент:
  presence_update     — обновление статуса пользователя
  call_incoming       — входящий звонок (from_user, call_type, offer)
  call_accepted       — звонок принят (answer SDP)
  call_rejected       — звонок отклонён
  call_ended          — звонок завершён
  call_busy           — абонент занят
  ice_candidate       — ICE кандидат для WebRTC
```

### Запись звонков (Call Logs)

Каждый звонок фиксируется в `call_logs`:
- caller_id, callee_id, tenant_id
- outcome: `missed` / `answered` / `rejected` / `busy`
- duration_sec, call_type, started_at, ended_at

### API

```
GET  /presence/status                — мой текущий статус
PUT  /presence/status                — установить статус
GET  /presence/users                 — статусы всех сотрудников тенанта
WS   /presence/ws/{user_id}          — WebSocket для звонков и статусов
GET  /presence/call-permissions      — матрица разрешений
POST /presence/call-permissions      — обновить разрешение
GET  /presence/notification-settings — настройки уведомлений по ролям
POST /presence/notification-settings — обновить настройки
```

## Аудит и мониторинг

### Аудит (audit_log + activity_log)

**Журнал аудита** (`audit_log`) — формальные изменения с состоянием до/после:
- Создание/обновление/деактивация сотрудников
- Корректировки финансового реестра
- Изменения настроек
- Выплата/отмена бонусов
- Создание/обновление партнёров и скидок

**Журнал активности** (`activity_log`) — операционные события:
- Создание направления
- Подтверждение направления (QR/код)
- Запрос отмены
- Выплата бонусов

Раздел **Аудит** в AdminLayout показывает объединённый журнал из обеих таблиц (endpoint `/audit/feed`), с badge источника (📋 аудит / 📝 активность).

Фильтрация: по действию, типу сущности, периоду (7/30/90/365 дней).

### Мониторинг системы

Раздел **Мониторинг** в AdminLayout:

**Сервер:**
- CPU %, RAM %, Disk % — с gauge-барами и цветовой индикацией (жёлтый/красный при превышении)
- Uptime сервера

**Сервисы:**
- PostgreSQL: статус, размер БД, количество соединений
- Redis: статус, используемая память, ключи
- МИС Renovatio: статус подключения, последний успешный запрос

**Контейнеры Docker:**
- Статус и uptime каждого контейнера
- Цветовая индикация (UP/DOWN)

**Логи контейнеров:**
- Просмотр последних N строк логов любого контейнера (backend/frontend/db/redis)
- Цветная подсветка ERROR/WARNING строк

**Анализ БД:**
- Список таблиц с количеством строк, удалёнными записями, размером
- Рекомендации по VACUUM

**На главной панели:**
- 4 плитки (API / База данных / Redis / МИС) — кликабельные, переход в мониторинг
- Автообновление каждые 30 секунд

### API мониторинга

```
GET /monitoring/health    — быстрая проверка всех сервисов
GET /monitoring/system    — полная системная информация
GET /monitoring/metrics   — метрики производительности API
GET /monitoring/logs      — логи контейнера
GET /monitoring/db-analysis — анализ таблиц БД
GET /monitoring/security-audit — безопасность (failed logins, recent activity)
```

## Мульти-тенантность

Архитектура: **shared database, separate schemas via tenant_id**.

### Тенант (Tenant)

- Изолированные данные: `tenant_id` на всех таблицах
- Собственный `slug` (поддомен)
- Брендинг: `primary_color`, `sidebar_color`, логотип
- Конфигурация модулей: `tenant_modules` (переопределение фич плана)

### Управление тенантами (Super Admin)

Раздел **Платформа** → вкладки:
- **Метрики**: количество тенантов, пользователей, направлений, подписок по статусу/плану
- **Тенанты**: таблица всех тенантов с управлением (активация, модули, подписка)
- **Биллинг**: MRR платформы, все подписки с суммами

### Создание нового тенанта

Кнопка **"Новый тенант"** → форма:
- Название и slug
- Первоначальный план
- Данные первого admin (имя, username, пароль, цвет)
- Создаёт: тенант + первый пользователь + tenant_license + настройки по умолчанию

### Управление модулями тенанта

Кнопка **"Модули"** в строке тенанта → настройка включения/выключения отдельных фич:
- `enabled` — явно включить (перекрывает план)
- `disabled` — явно выключить
- `null` — наследовать от плана

### Feature Gates

Трёхуровневый приоритет:
1. `tenant_modules` (явное переопределение)
2. `tenant_licenses.plan` → `PLAN_FEATURES[plan]`
3. Дефолтный план (basic)
